**Gate Position**: **FL-01G-A (Write Contract & Persistence Safety Gate)**

## 1. Safety Gate Purpose & Architecture

The **Persistence Safety Gate** acts as an unbypassable software firewall situated between the analytical pipeline (FL-01A..FL-01F) and the operational database write service:

```
┌─────────────────────────────────────────────────────────────┐
│             ANALYTICAL ENGINE PIPELINE (FL-01A..F)          │
│  Outputs Resolution State, Candidate Hypotheses & Evidence  │
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────┐
│              FL-01G PERSISTENCE SAFETY GATE                 │
│                 [10 Mandatory Checkpoints]                  │
│                                                             │
│  [1] Pipeline Signature  [6] Fingerprint Integrity         │
│  [2] Multi-Hypothesis    [7] Replay / Idempotency Check     │
│  [3] Selection Rule      [8] Atomic Transaction Boundary    │
│  [4] Evidence Provenance [9] Immutability & Audit Staging   │
│  [5] Safety Invariants  [10] No Auto-Dispatch Guard        │
└──────────────┬──────────────────────────────┬───────────────┘
               │ PASS                         │ REJECT
               ▼                              ▼
┌──────────────────────────────┐┌──────────────────────────────┐
│  DATABASE WRITE TRANSACTION  ││    DETERMINISTIC REJECTION   │
│     (FL-01G-B+ LOCKED)       ││   Zero DB Mutation (Δdb = 0) │
└──────────────────────────────┘└──────────────────────────────┘
```

**Core Safety Mandate**:
No database transaction may be opened and no SQL `INSERT` may be executed without first passing all 10 checkpoints of the Persistence Safety Gate.

## 2. The 10 Mandatory Safety Checkpoints

### Checkpoint 1: Pipeline Signature & Version Completeness
- Verifies that input payload was generated by authoritative pipeline components:
  - FL-01B version (`FL-01B-1.0`)
  - FL-01C version (`FL-01C-1.0`)
  - FL-01D version (`FL-01D-1.0`)
  - FL-01E version (`FL-01E-1.0`)
  - FL-01F version (`FL-01F-1.0`)
- If any required subsystem metadata or version string is missing, reject with `SAFETY_GATE_REJECT_PIPELINE_INCOMPLETE`.

### Checkpoint 2: Multi-Hypothesis Structural Integrity (1:N:N)
- Verifies that candidate hypotheses are preserved in a multi-record array (`hypotheses` length $\ge 1$).
- Rejects any attempt to collapse multiple branch hypotheses into a single flat coordinate or pole.
- Rejection Code: `SAFETY_GATE_REJECT_FLAT_SCHEMA_VIOLATION`.

### Checkpoint 3: Hypothesis Selection Consistency Guard
- Enforces strict relationship between analytical resolution state and `selected_hypothesis_id`:
  - If `resolution_state == 'SINGLE_CONFIDENT_HYPOTHESIS'`:
    - `selected_hypothesis_id` MUST NOT be null and MUST match an existing active hypothesis in the payload.
  - If `resolution_state` is one of `['BRANCH_AMBIGUITY', 'MULTIPLE_COMPATIBLE_HYPOTHESES', 'EQUALLY_PROBABLE', 'UNRESOLVED', 'NO_VALID_HYPOTHESIS']`:
    - `selected_hypothesis_id` **MUST BE STRICTLY NULL**.
- Rejection Code: `SAFETY_GATE_REJECT_INVALID_SELECTION`.

### Checkpoint 4: Evidence Provenance & Integrity
- Every evidence item attached to each hypothesis must possess complete provenance fields:
  - `type` (One of 8 recognized types)
  - `status` (`SUPPORTING`, `CONTRADICTING`, `NEUTRAL`, `UNAVAILABLE`, `UNKNOWN`)
  - `source_table`, `source_id`, `relation`
- `UNKNOWN` evidence is verified to NEVER be used as negative or disqualifying evidence.
- Fabricated evidence (e.g. unverified inspection findings or fake probabilities) is strictly prohibited.
- Rejection Code: `SAFETY_GATE_REJECT_EVIDENCE_INTEGRITY_VIOLATION`.

### Checkpoint 5: Safety Invariant & AI Firewall
- Asserts the following boolean invariants:
  - `ai_used === false`: Zero machine learning or LLM inference was used in determining fault point or confidence.
  - `topology_mutation === false`: Zero modification of network topology or switch statuses.
  - `asset_mutation === false`: Zero modification of pole/asset attributes.
  - `temuan_mutation === false`: Zero modification of inspection finding records.
  - Zero nearest-asset or nearest-GPS snapping parameters present in payload.
- Rejection Code: `SAFETY_GATE_REJECT_SAFETY_INVARIANT_BREACH`.

### Checkpoint 6: Canonical Event Fingerprint Integrity
- Calculates the canonical SHA-256 fingerprint from the physical invariants:
  $$\text{event\_fingerprint} = \text{SHA-256}(\text{penyulang\_id}, \text{ftu\_id}, \text{fault\_time}, \text{fault\_type}, I_a, I_b, I_c, V, Z, \text{source\_distance}, \text{raw\_payload})$$
- Confirms that the provided fingerprint matches the calculated fingerprint exactly.
- Rejection Code: `SAFETY_GATE_REJECT_FINGERPRINT_MISMATCH`.

### Checkpoint 7: Replay & Idempotency Audit
- Checks whether `event_fingerprint` already exists in the authoritative registry.
- If fingerprint exists:
  - Halts write execution immediately.
  - Returns deterministic `REPLAY_DETECTED` payload without error or duplicate insertion.
  - Signals: `SAFETY_GATE_SIGNAL_REPLAY_DETECTED`.

### Checkpoint 8: Atomic Transaction Boundary Guarantee
- Requires caller to provide an active transaction manager capable of atomic `BEGIN`, `COMMIT`, and `ROLLBACK`.
- Asserts that foreign key referential integrity checks are enabled.
- Rejection Code: `SAFETY_GATE_REJECT_TRANSACTION_UNAVAILABLE`.

### Checkpoint 9: Immutability & Audit Trail Staging
- Verifies that a valid `fault_event_audit` payload is staged alongside the event data with:
  - `action = 'EVENT_CREATED'`
  - `actor_type = 'SYSTEM_ENGINE'`
  - `request_fingerprint`
- Rejection Code: `SAFETY_GATE_REJECT_AUDIT_NOT_STAGED`.

### Checkpoint 10: Human Review & No Auto-Dispatch Guard
- Enforces that operational status is set to `PERSISTED` (awaiting operator review).
- Automated dispatch flag (`auto_dispatch`) MUST BE FALSE.
- Rejection Code: `SAFETY_GATE_REJECT_AUTO_DISPATCH_PROHIBITED`.

## 3. Pre-Commit Checklist Matrix

| # | Safety Checkpoint | Target Assertion | Failure Handling | Rejection Code |
| :-: | :--- | :--- | :--- | :--- |
| **01** | Pipeline Signature | Subsystem versions match `FL-01B..F` | Reject before DB lock | `SAFETY_GATE_REJECT_PIPELINE_INCOMPLETE` |
| **02** | Multi-Hypothesis Structure | Hypotheses array preserved ($N \ge 1$) | Reject before DB lock | `SAFETY_GATE_REJECT_FLAT_SCHEMA_VIOLATION` |
| **03** | Selection Null Rule | `selected_id == null` when ambiguous | Reject before DB lock | `SAFETY_GATE_REJECT_INVALID_SELECTION` |
| **04** | Evidence Provenance | Complete source table/id/relation | Reject before DB lock | `SAFETY_GATE_REJECT_EVIDENCE_INTEGRITY_VIOLATION` |
| **05** | AI & Mutation Firewall | `ai_used: false`, 0 mutation flags | Reject before DB lock | `SAFETY_GATE_REJECT_SAFETY_INVARIANT_BREACH` |
| **06** | Fingerprint Integrity | SHA-256 matches canonical fields | Reject before DB lock | `SAFETY_GATE_REJECT_FINGERPRINT_MISMATCH` |
| **07** | Replay Audit | Fingerprint uniqueness verified | Return `REPLAY_DETECTED` | `SAFETY_GATE_SIGNAL_REPLAY_DETECTED` |
| **08** | Transaction Boundary | ACID transaction wrapper confirmed | Reject before write | `SAFETY_GATE_REJECT_TRANSACTION_UNAVAILABLE` |
| **09** | Audit Trail Staging | Audit record prepared for insert | Reject before write | `SAFETY_GATE_REJECT_AUDIT_NOT_STAGED` |
| **10** | No Auto-Dispatch | `auto_dispatch: false`, status `PERSISTED` | Reject before write | `SAFETY_GATE_REJECT_AUTO_DISPATCH_PROHIBITED` |

## 4. Replay Response Specification

When Checkpoint 7 identifies an existing event with an identical fingerprint, the service must return a structured response rather than raising an unhandled database unique constraint exception:

```json
{
  "status": "REPLAY_DETECTED",
  "message": "Telemetry event has already been persisted in authoritative database. Idempotency guaranteed.",
  "event_fingerprint": "b7a9c3f1e5...",
  "existing_event_id": 142,
  "existing_resolution_state": "BRANCH_AMBIGUITY",
  "hypotheses_count": 2,
  "mutations_performed": 0
}
```
